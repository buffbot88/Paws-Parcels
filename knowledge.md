## What this is
**Paws & Parcels** — a cozy, browser-based **2.5D online RPG (MMORPG-lite)** where the player is a tiny animal courier in a shared magical forest. The game is **server-authoritative**: the server owns all gameplay state; the client renders intents. No permanent failure states, no PvP, no gore.

The world was REPLACED (Aug 2026): the obsolete Clover Village layout was deleted and a NEW authored 75×75 village shipped; maps are live again end-to-end.** The client is the Phaser 4 foundation (one walkable hub zone, 5 NPCs, DOM dialogue) rebuilt around **Clover Village** (`zone-clover-village`, `src/data/maps/clover-village.json` — generated by `scripts/generate-clover-village.mjs` to match the approved reference overview). **The NEW Clover Village is a compact 75×75 world map**: Courier Square plaza at `(37,28)` (spawn `(37,31)`), two-story Post Office north (Building 17 art, footprint x33-41/y15-22), Café west (Building 16), Research Shop east (Building 5), Florist southeast (Building 3), fenced open Moss garden (x40-52/y40-47, no building), two cottages, NW pond + Rabbit Burrow landmark, SW Hollow Oak clearing (`object-hollow-oak` — resolves the Golden Acorn quest), SE pond + picnic clearing, and a lamp-lined southern road through a banner gate to the Happy Valley transition at `(37,74)`; the camera zooms to 0.8 (~25×14 tiles). Ground tiles are **procedurally textured** (`src/game/TileTextures.ts` — deterministic seeded canvas detail: grass speckles, path stones, plank floors, brick walls, water waves, foliage), and a **DOM minimap overlay** (`src/ui/Minimap.ts`, bottom-right, collapsible) shows terrain, NPCs/landmarks/transitions, other couriers (blue) and monsters (red) with the player marked by a ringed dot; it pre-renders terrain per zone and redraws the live layer each frame. The bottom-left glass chat panel sends authenticated same-zone messages only. `npm run visual:history` compares archived `visual-review*.json` reports from `tmp/` and `reports/`, tracking recurring category/target issues, severity, confidence, and overall score trends in `reports/visual-history.json`. Dev tool: `npm run tiles:loop` renders the tile textures to PNGs (`scripts/render-tiles.mjs`, software rasterizer sharing the `src/game/tilePalette.ts` params) and asks the **local VL** to critique them (`scripts/ai-tile-review.mjs`, reuses `ModelInstance` + `GameBrain`, spawns/reuses the game-owned instance). `npm run tiles:tune` (`scripts/auto-tune-tiles.mjs`) feeds the VL's per-tile scores back **automatically**: it adjusts the shared palette (contrast → dark/light pairs, noise → detail counts) and rewrites `DEFAULT_TILE_PALETTE` in `tilePalette.ts`, so a rebuild ships the tuned look. The 450M's hue naming is unreliable on mid-greens and its scores are noisy (temperature 0.7) — compare against the printed ground-truth center-averages and use `--dry-run` / `--iterations N` before committing to a long run. ## AI game engine (Phase 4 experimental)

A game-owned **LFM2.5-VL-450M** (Q8 + vision projector) llama-server instance backs NPC dialogue and monster decisions. It is **power-managed** and fully separate from the ASHAT Hub's always-on pair (ports **3001/3002** — those are alpha-server's and are **never touched**):

- **Lifecycle** (`server/src/ai/ModelInstance.ts`): spawned on demand, `/health`-polled (5.4s warm on this box), spun down after `ai.idleMs` (10 min) without requests, and stopped on server shutdown. A failed warm-up is remembered for 30s (`RETRY_AFTER_FAILURE_MS`) so a broken instance falls back fast instead of blocking a request on a fresh spawn. Binary overridable via `LLAMA_SERVER` env. Injectable `spawn`/`fetchHealth` for tests.
- **Brain client** (`GameBrain.ts`): OpenAI-compatible (`/v1/chat/completions`), `ai.requestTimeoutMs` (4s) abort, circuit breaker (3 failures → 60s), **never throws** — every failure resolves null and callers use the deterministic fallback.
- **Monster decisions** (`MonsterBrain.ts` + `monsterStore.ts`): one world-brain call per zone per 5s for the most "interesting" monster (aggro + player-near, HP tiebreak), fed an 11×11 ASCII map (`prompts.ts`) as cheap vision. Decisions override the deterministic AI for that monster; any failure or unparseable JSON **clears the zone's override** so deterministic AI is fully back in charge. Fire-and-forget — the 20 Hz tick never awaits the model.
- **NPC dialogue** (`POST /api/npc/talk`, `routes/npc.ts`): auth'd (JWT), per-account rate limit (`ai.npcTalkMinIntervalMs`, 6s), optional client canvas snapshot → **true VL vision**. Responses are `{line, source: "ai"|"canned"}`; the client opens canned dialogue immediately and appends the AI line. Screenshots are **JPEG-only** and validated by reading SOF header dimensions (`server/src/ai/image.ts`) to block decompression-bomb OOMs on the 1-core host.
- **Config** (`server_config.json` → `ai.*`, default disabled): `enabled`, `port` (3101), `modelPath`/`mmprojPath`, `idleMs`, `warmupTimeoutMs`, `requestTimeoutMs`, `monsterDecisionIntervalMs`, `maxTokensMonster` (40), `maxTokensNpc` (160), `npcTalkMinIntervalMs`. Model files live at `/home/opc/AshatPlatform/models/`.
- **Production wiring**: the game server listens on **127.0.0.1:3003** (`server.port` — moved off 3001 so it can't clash with the Hub's llama pair); the model instance is spawned by the game server on demand (port 3101) and pre-warmed when a player joins a zone. Live-verified: text + VL chat work end-to-end.

## Admin Control Panel (foundation + player tools, built)
The internal management surface lives at **`/admin.html`** (second Vite entry alongside the game's `index.html`; served same-origin by the game server in production, `http://localhost:5173/admin.html` under the Vite dev proxy). It reuses the game client's session storage keys (`paws.auth.token`, `paws.auth.account`) and the session cookie — no separate login.

- **Tiers, not roles:** `server/src/models/Admin.ts` maps ASHAT Hub roles to ordered tiers (none < support < moderator < admin < developer) via `DEFAULT_ROLE_TIERS`, overridable in `server_config.json` → `admin.roleTiers`. Handlers gate via `resolveActor(req, res, minTier)` in `server/src/routes/admin.ts`; the old `requireAdmin` (exact `Admin` role) still guards visual-capture only.
- **Fine-grained permissions (spec §70–71):** migration `015_admin_roles.sql` adds `admin_roles` + `admin_role_permissions` (seeded: developer/administrator/game_master/content_designer/liveops/support) and `admin_user_roles`. Roles layer on top of tiers: `resolveActorWithPermission(req, res, minTier, permission)` passes if the actor's tier meets the baseline OR holds the permission via an assigned role (tier always wins for developers). APIs: `GET /api/admin/roles` (matrix + caller info incl. `canManageRoles`), `PUT /api/admin/roles/:roleKey/permissions` (system roles never lose their last manage_roles holder — guardrail), `PUT /api/admin/users/:id/roles`. Panel screens: Roles & Permissions (matrix with per-cell confirm) and Admin Users (role chips + assign/revoke) in `src/admin/screens/{roles,adminUsers}.ts`. Tests: `tests/server/admin-roles.test.ts`.
- **Audit:** every admin mutation inserts into `admin_audit_log` (migration `014_admin_panel.sql`) with before/after JSON states, reason, environment label, request id, and IP. Read APIs: `GET /api/admin/audit` (+`/:id`). The economy ledger `audit_economy_events` also receives rows for inventory/EXP changes.
- **Ban enforcement is real:** `requireAccount` (server/src/middleware/auth.ts) checks `accounts.status` and returns 403 `ACCOUNT_SUSPENDED` for `suspended`/`banned` — both HTTP and (via ws-token → same helper) WS paths. `GameServer.disconnectCharacter` closes live sessions and removes the player from all zones; admin suspend/ban/teleport call it through the `AdminRuntime` bridge (`server/src/ws/adminRuntime.ts`, wired in `index.ts` after GameServer construction).
- **Server settings** live in the `server_settings` key-value table (`exp_rate`, `drop_rate`, `honor_rate`, `max_concurrent_players`, `level_cap`; migration 014 seeds defaults). `PUT /api/admin/settings` (tier admin, reason required) validates ranges and audits; gameplay loops do NOT consume exp/drop rates yet — the panel surfaces them honestly as stored settings. `level_cap` currently mirrors `MAX_LEVEL` in `server/src/models/leveling.ts`.
- **Frontend** (`src/admin/`): vanilla TS DOM like the game UI — `main.ts` (boot/tier check), `router.ts` (hash router; `add()` strips a leading `#` so patterns work with or without it), `shell.ts` (240px forest-green sidebar, 64px top bar, LIVE banner when `runningInProduction`), `api.ts` (fetch wrapper), `ui.ts` (el helper accepting `onclick:` props, modals with Level-3 typed confirm, toasts, skeletons), `screens/` (dashboard, players, playerDetail, audit, settings). Design tokens in `styles/admin.css` match the admin spec (§3 colors, §9 environment badges).
- **Level-3 typed confirmation** pattern: suspend/ban modals require typing `SUSPEND <username>` / `BAN <username>`; the server re-validates the phrase (`CONFIRMATION_REQUIRED` otherwise) — never trust the client.
- **Session hardening** (`server/src/auth/adminHardening.ts`): (1) CSRF double-submit on all `/api/admin/*` mutations — middleware (`middleware/index.ts`) mints a `paws_csrf` cookie (64-hex) on admin GETs and rejects mutations without a matching `X-Admin-CSRF` header (403 `CSRF_CHECK_FAILED`); `/api/admin/csrf` is exempt so the panel can bootstrap. (2) Short-TTL step-up tokens: `POST /api/admin/step-up {reason}` (min tier support) mints an HMAC-signed, account-bound, single-use token (5-min TTL) audited as `step_up_issued`; Level 3 routes (`POST /api/admin/players/:id/status`) require the `X-Admin-Step-Up` header — 401 `STEP_UP_REQUIRED` when absent, 403 `STEP_UP_REPLAYED` on reuse (JTI replay set). (3) The panel UX chains them: typed-phrase modal → re-auth modal (reason) → step-up mint → mutation with both headers (`api.stepUp()` + `stepUpHeaders()` in `src/admin/api.ts`, `reAuthModal` in `src/admin/ui.ts`). Tests: `tests/server/admin-hardening.test.ts`.
- **Player detail tabs** fetch inventory/quests through the player-facing `GET /api/characters/:id/profile` endpoint with the admin's own JWT (the admin API doesn't duplicate profile serialization yet).
- Deferred admin phases (content editors, draft/publish versioning, market/seasons/zones, Ctrl+K search, node quest designer, permission matrix) are listed in ROADMAP.md §2 — do not stub them.

## Quickstart
**Client (Phaser 4 app) + server (Node/TS, `server/`) both live in this repo.**
- Setup: `npm install`
- Dev client: `npm run dev` (localhost:5173) — Boot → Preloader → Overworld (walk with WASD/arrows/drag)
- Dev server: `npm run dev:server` — SQLite at `server/data/paws-and-parcels.sqlite` (auto-created + migrations 001–012 run on boot), health check `http://localhost:3001/api/health`, WebSocket on `/ws`. **Production on this VPS binds 127.0.0.1:3003** (3001/3002 belong to the Hub's llama pair) — the `paws-and-parcels.service` systemd unit runs `node --import tsx server/src/index.ts` from the repo root
- Build: `npm run build` (outputs `dist/`; `base: './'` for static hosting)
- Typecheck: `npm run typecheck`
- Test: `npm test` (Vitest) — 486 tests in `tests/`
- Admin panel (dev): `npm run dev` then `http://localhost:5173/admin.html`; production: `https://<host>/admin.html` (served from dist by the game server)
- Content validate: `node scripts/validate-content.ts` (also `npm run validate`)

**Gotcha:** the repo folder name contains `&` (`Paws&Parcels`), which breaks npm's `node_modules/.bin` PATH shims on Windows. The npm scripts therefore invoke the tools via explicit relative paths (`node node_modules/typescript/bin/tsc --noEmit`, `node node_modules/vitest/vitest.mjs run`, `node node_modules/vite/bin/vite.js`) — do not change them back to bare `tsc`/`vitest`/`vite`.
- **JSON imports:** Node 26's native TS runner requires `with { type: "json" }` on JSON imports (see `src/game/Maps.ts`) — plain JSON imports work under Vite/Vitest but crash the validate CLI. Use the import attribute.

## Planned stack & architecture
- **Client:** Phaser 4 (Canvas/WebGL, depth-sorted isometric/pseudo-3D). Game config: 960×540, `Scale.FIT` + `CENTER_BOTH`, parent `#game-container`, min width 320px
- **Server:** Node/TS (separate process, same monorepo or sibling package). WebSocket + HTTP. Containerized.
- **Database:** SQLite — accessed only by the server. Auth delegated to ASHAT Hub OIDC (no local passwords).
- **UI:** DOM-over-Canvas — all menus/dialogue/inventory/shop/settings in HTML/CSS layered above the canvas, never built in Phaser. Bridge via an event-emitter pattern.
- **Persistence:** SQLite for all gameplay state; localStorage holds the server-issued auth session (JWT, lifetime per server config) and client settings, never authoritative gameplay state.
- **Maps:** custom JSON (ASCII `rows` + spawn/transitions); **assets:** Aseprite → sprite sheets + JSON atlases
- **Data:** JSON content files under `src/data/` are authoritative static content; SQLite stores player state, ownership, progression, and audit history only
- **Deployment:** single-process hosting — one Node server serves the built client (`dist/` via `server/src/static/client.ts`) + the HTTP API + the WebSocket endpoint on one port, so the client's same-origin relative URLs just work. Hosts: Render (web service), Fly.io, a VPS, or Oracle Cloud Always-Free (`npm run build && npm run start:server`; `$PORT` env is honored for PaaS; `scripts/write-server-config.mjs` + `render.yaml` generate `server_config.json` from env vars). Vercel/Netlify can host the client alone, but the game server cannot run on serverless (connection lifetime caps + read-only/ephemeral filesystem break long-lived WebSockets and SQLite writes).
- **VPS layout (pawsandparcels.agpstudios.org):** Apache serves `dist/` (DocumentRoot = project `dist/`, SPA `.htaccess` auto-copied on build); the Node game server runs as a systemd service (`paws-and-parcels.service`) bound to `127.0.0.1:3003` behind Apache's `/api` + `/ws` reverse proxy, so the client stays same-origin. The SQLite DB lives outside the webroot at `/home/opc/pawsandparcels/data/`. The client's runtime config is `client-config.txt` (named `.txt` because the ASHAT Hub Apache layer denies all `*.json` responses below the docroot). The vhost (`/etc/httpd/conf.d/pawsandparcels.agpstudios.org.conf`) is auto-generated by ASHAT Hub provisioning — re-provisioning overwrites the DocumentRoot/proxy edits (backup: `*.conf.bak.*`).
- **Sign-in is live end-to-end** via the ASHAT Hub OIDC issuer `https://www.agpstudios.org/api/oauth` (discovery `https://www.agpstudios.org/api/oauth/.well-known/openid-configuration`). The Hub's `oauth_clients` row for `paws-and-parcels` registers the production callback `https://pawsandparcels.agpstudios.org/oidc-callback.html`; the game's `server_config.json` `oidc.discoveryUrl`/`oidc.issuer` point at the `www.` host — do not revert to `agpstudios.org`, the Hub signs with the `www.` issuer.
- **Static assets go to `/static/`, not `/assets/`:** the ASHAT Hub server config (`/etc/httpd/conf.d/ashathub.conf`) globally `Alias /assets/`, `/css/`, `/js/`, `/images/` to the Hub's own public dir on **every** vhost — so game assets under `/assets/` were hijacked and SPA-fallbacked to `index.html` (text/html MIME errors in the browser). Vite's `build.assetsDir` is set to `"static"` to dodge those aliases; do not revert it.
- **Hub-side OIDC gotchas (fixed 2026-08-10):** the Hub's authorize endpoint 500'd on every request (`OAuthController::readAuthorizeParams` called non-existent `RequestContext::queryData()`/`postData()` — now uses `query()`/`str()`), its global CSRF gate blocked the game server's server-to-server POST to `/api/oauth/token` (that endpoint is now exempt; the interactive login POST still enforces CSRF), and the authorize/error views (`oauth_authorize.php`, `oauth_error.php`) were missing and had to be created. The Hub logs caught exceptions with full stack traces to `storage/logs/error.log` via `Router::handleException`.

## Authority rules
- **Client input is untrusted.** Server validates all intents: movement, attack, interact, quest accept, equip, craft.
- **Combat math is server-side.** Damage, crits, defeat, respawn — all server-computed.
- **Quest completion is server-validated.** Prerequisites, delivery targets, gating.
- **Inventory is server-authoritative.** Ownership, stacks, slots, equipment.
- **Economy is audited** via `audit_economy_events` table.

## Conventions
- **Follow `VOWS.md`:** no shortcuts/mock/boilerplate/underbuilding; no hallucinating or assuming — ask the user; present a build plan and get user approval BEFORE implementing; docstrings max 1–2 sentences; gather all context first, then exactly one planning pass

- **Game feel targets:** cozy-first, no grinding, no permanent progress blockers; initial load <5s, 60 FPS desktop / 30–60 FPS mobile; minimum width 320px

- **Clover Village ground art:** the pack's land_1/road_5 tiles render flat/blocky in-engine. `scripts/generate-ground-assets.mjs` derives two new seamless textures (meadow from re-lit land_1, road from de-featured road_5) into `reference/assets/new/CloverValley/Ground/`; regenerate with `node scripts/generate-ground-assets.mjs` (deterministic), then `npm run assets:inventory`.

Idempotent; rerun then `npm run assets:inventory`. Shares the PNG codec in `scripts/lib/png.mjs` with the ground generator.
- **Happy Valley ground art:** the valley's placeholder tileset (flat color fills) is replaced by authored surfaces via the same pipeline as the village: `generateValleyMeadow()` (the pack has no full-bleed painted field — its 56 Ground tiles are ~1.5% opaque cutouts — so the base is a flat tone sampled from the pack's painted grass patches, hue ~93deg/sat 0.43, plus grain + toroidal mottle + strokes with valley seeds) and `generateValleyPath()` (same road_5 pipeline, own fleck seed). Wired by `addHappyValleyGround` in happyValleyAssets.ts, called from OverworldScene for the valley zone; collision tiles (water/trees) stay on the tilemap. Files: reference/assets/new/HappyValley/Ground/valley-meadow.png, valley-path.png. Regenerate with `node scripts/generate-ground-assets.mjs`, then `npm run assets:inventory`.
- **Clover Village plaza + canopy:** Courier Square is now paved — `generatePlaza()` (toroidal 8x8 grid-bond gray-stone cobble, soft pastel ~sat 0.09, moss/accent stones) renders on the square's P tiles (x29-44, y25-35) via the `plaza` texture key in addCloverVillageGround; a flower-front ring marks the tilemap's X-flower cluster as the central bed; and a ~59-piece tree/greenery canopy ring (spread >=4 tiles, clear of interactables/spawn/transitions) frames the map edges toward the reference look.
- **Clover Valley reference props:** the five set pieces the reference overview shows but the pack had no art for — café outdoor tables/stools, raised garden beds, cottage clotheslines, the grand southern entrance arch (stone bases, lanterns, white clover banner), and pond lily pads — are authored cutouts painted procedurally in the pack's pastel language. `scripts/generate-clover-valley-props.mjs` writes them to `reference/assets/new/CloverValley/Props/` (deterministic, idempotent), then `npm run assets:inventory`. Wiring lives in cloverVillagePlacements.ts (keys cafeTable/gardenBed/clothesline/entranceArch/lilyPads + placements: 3 café tables, 4 garden beds in Moss's garden, clotheslines by both cottages, the gate arch at (37,72.5), lily pads on both ponds) and cloverVillageAssets.ts (sourceAssets globs). All five are transparent cutouts like the rest of the pack — unlike route-clutter.png, which stays descoped (full-bleed painting).
